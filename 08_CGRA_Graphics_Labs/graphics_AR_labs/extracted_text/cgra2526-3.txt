Pipelines
The evolution of OpenGL framework both on desktop computers and mo-
bile devices was clearly boosted by the evolution of the graphics processing
engines (GPU)s that keep becoming more powerful every day. In fact, the
architectural changes in hardware were introducing more and more com-
puting power that could not be easily exploited by the traditional API.
This pushed the progressive evolution from the ﬁxed graphics pipeline in
versions 1.X, to the possibility of optionally supplying vertex and fragment
shaders in version 2.0, until their mandatory use from version 3.1 on.

Starting with the vertex shader, we may say that its primary purpose
is to apply all the necessary geometric transformations to the vertices that
compose each part of the models (or scene) ﬁrst, and then compute their
projection (in the image plane). In reality this projection is not performed
as expected from 3D space to a 2D image plane, but we may think of it like
that by now.
This shader receives and processes each of the vertices, along with some
variables that will inﬂuence the transformations applied. For each vertex
it computed the position of the corresponding projections in the image
plane. This means that the C/C++/Python/JavaScript program will pre-
pare these variables and pass them to the GPU along with the model vertices
to be projected.

The vertex shader
The shaders can be thought of as programs written in a C dialect, that can
be put together to form a program. Let’s start with the ﬁrst one that will
process our data, the vertex shader.
The vertex shader will basically process the vertices coordinates and
manipulates them before passing them to the next step in the pipeline. It
may also do colour and other data processing that will be passed down the
pipeline to the fragment shader through specially declared variables.

The fragment shader
The fragment shader is responsible for computing the ﬁnal colour of each
fragment ("pixel") that becomes visible after projecting the model elements
into the output framebu !er. Note that if your scene is composed of multiple
objects, each of them will be processed by one shader program, and those
shader programs may be the same or totally di !erent from object to object.
The same applies naturally to the fragment shader.
Like the vertex shader that is going to be called repeatedly to process
one vertex at a time, the fragment shader is going to process individually
each fragment. So think of it as “the code that computes the ﬁnal color for
one single fragment” that will be applied to all of them.

In the above example it may seem that it receives the exact value passed
from the vertex shader exColor, but this is not really true. In fact there are
(normally) much more fragments than vertices. If the primitives you are
drawing are lines, then you have processed the two extremity vertices and
passed only two colours to the next stage. As there are a set of fragments
between these two extremities, each of them will receive a color (rgb) on this
"varying" variable which results from the interpolation of the two extremity
colours. So if there is one black (0,0,0) vertex and one white (1,1,1), the
fragments in between will receive intermediate grey level values, depending
on how close they are to one or another. in the case of triangles, the
interpolation will be bilinear between the 3 colours of the 3 vertices.
The output will be written in gl_FragColor, another standard variable
that e !ectively consists in the color that will be visible for that fragment
in the case it will not be overlapped by another one. Note that the output
colour has four components where the fourth is an opacity/transparency
factor.

vertex for performing its computations. So it may be seen as having a
di!erent program (or thread) for each vertex. However it is common to
have the processing of the whole set of vertices controlled by some parameter
that may change during run time. This can be one or more scalars, vectors.
and/or matrices. 2
For this a di !erent type of data exists which are called uniforms and
consists of one input parameter that is shared between (and common to)
the whole set of vertices (or fragments) when processed.
